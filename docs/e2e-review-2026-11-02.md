# Dummy-city end-to-end review — 2 November 2026

The tested local flows pass after fixing attendance upload and date comparisons. This is a local integration result, not a production certification.

## Environment and evidence

Created **E2E Municipal Test City** in a new, isolated PostgreSQL cluster on loopback port 54329. The application database schema and integrity constraints were loaded into a disposable database. Requests used the real Express routes, JWT password login, Prisma and PostgreSQL. The browser loaded the real frontend and forwarded its API requests to this local backend; responses were not replaced with fixtures.

Only bootstrap authentication and location-master reference records were seeded directly. City onboarding, personnel, geography, registrations, approvals, assignments, targets, inspections, attendance import and plant Excel import used actual HTTP endpoints. Plant catalogue/parameter reference configuration was seeded for the dummy MRF.

Production data and existing real city accounts were not changed.

## Fixes found through real database testing

1. **Attendance upload failed with PostgreSQL UUID type errors.** Parameterized raw SQL supplied text parameters for UUID columns. Added explicit UUID casts to batch/record identifiers and batch updates.
2. **Attendance reupload and selected-date comparisons depended on the database timezone.** A date column was compared with a timestamp parameter; the existing row could be missed during duplicate detection. All raw attendance date predicates and upload date values now use date-only strings explicitly cast to PostgreSQL `date`. Reupload now reports one updated row and zero inserted rows; single-day and wider-range summaries retain one present record.

No database migration is required for these fixes. Deploy the backend change before expecting production attendance imports to use it.

## Arithmetic cross-check after KML import

The dummy city has 10 registered entities, five completed inspections and five unique inspected entities. Thus coverage is **5 / 10 = 50%** for each tested range, because all five visits occurred on 2 November.

| Selected dates | Inspection records | Completed | Unique inspected | Coverage | Assigned target | Target credit |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 2 Nov | 5 | 5 | 5 | 50% | 13 | 5 |
| 27 Oct–2 Nov | 5 | 5 | 5 | 50% | 91 | 5 |
| 1 Aug–2 Nov | 5 | 5 | 5 | 50% | 1,222 | 5 |

The target here is an **officer-assignment target**, not the entity inventory: each of the two jointly assigned Darogas has three Sweeping Beats, adding six officer/Beat assignments. The other module assignments add seven units. This produces 13 daily assigned units even though inventory has 10 entities. The saved 100% daily target and default assignment requirements preserve the backend rules. Coverage counts an entity once and does not duplicate it for shared Darogas or selected days.

## What remains unverified

- Live S3 uploads and AI image judgement: storage was isolated and AI disabled in this test.
- Connected Workforce/AttendEase and external Swachh services: isolated; their live provisioning, permissions, synchronization and availability were not tested.
- Physical mobile-app camera, device GPS, push notifications and app-build compatibility.
- Production deployment, production database migrations/state, and loading time at production data volume. Local synthetic data is not a production performance benchmark.
- Exhaustive combinations of every form input, historical record shape and concurrent change. Passing these checks does not establish that every possible path is defect-free.

## Repeating the review

Private backend harness: `tests/municipal-workflow.e2e.cjs`. Build the backend first, create a fresh local scratch database using the existing scratch setup script, then set `MUNICIPAL_E2E_DATABASE_URL` to its explicit loopback URL. The harness refuses other hosts/ports or non-`scratch_e2e_` database names and resets only that explicitly selected scratch database. `MUNICIPAL_E2E_SERVE=1` keeps its test HTTP server running for browser checks; its test-login/stop endpoints exist only in this harness.

Browser runner: `tests/e2e/municipal-browser.cjs`, using local frontend port 3000, test API port 4107 and headless Chrome debugging port 9336.

Local evidence: `.ui-review/municipal-e2e-results.json`, `.ui-review/municipal-browser-results.json`, `.ui-review/municipal-metrics.json`, suite logs and `e2e-real-commissioner.png` / `e2e-real-mobile.png`. These contain test evidence and are not application production data.
