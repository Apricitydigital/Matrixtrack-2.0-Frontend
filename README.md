# MatrixTrack 2.0 Municipal Command Center

React dashboard hosted by Next.js and connected to the existing MatrixTrack Express backend. PostgreSQL and Prisma remain in that backend. The dashboard no longer seeds demo data or saves changes to localStorage.

## Run locally

1. Copy `.env.example` to `.env.local` if you do not already have it. It points to `https://api.matrixtrack20.in`, matching the existing MatrixTrack frontend and its account database.
2. Run `npm install`, then `npm run dev` in this folder.
3. Open the URL printed by Vite and sign in with an existing Super Admin, City Admin, ULB Officer or Commissioner account.

To use the separate local/test backend, set `MATRIXTRACK_BACKEND_URL=http://127.0.0.1:4000` and `NEXT_PUBLIC_API_BASE_URL=/backend` in `.env.local` and keep that backend running. Its credentials and database may differ from production. Restart the development server after changing configuration. `.env.example` is only a template; editing it does not apply runtime settings. No database passwords, private API keys or service keys belong in this frontend.

For production, retain the existing `NEXT_PUBLIC_API_BASE_URL` HTTPS backend setting, or use `/backend` with Next.js's built-in rewrite to `MATRIXTRACK_BACKEND_URL` (default `https://api.matrixtrack20.in`). The backend must allow the dashboard origin when using a direct URL. Existing `VITE_API_BASE_URL` settings remain a fallback during transition.

## Integration

- Login and restored sessions: `/auth/login`, `/auth/me`. The bearer token is scoped to this dashboard's sessionStorage. Sign out clears this app's session; the existing server's `/auth/logout` does not invalidate JWTs.
- City directory, location master, onboarding, administrators and module provisioning: `/hms/*`.
- Personnel and registration approval/rejection: `/city/users`, `/city/super-admin-overview`, `/city/registration-requests/*`.
- Geography, beat creation and Daroga assignment: `/city/geo`, `/city/areas/*`.
- Sweeping, toilets, litter bins, Nala and CTU/GVP reports: `/modules/:module/records`, including subsequent pages. Escalation uses the module's existing workflow; the server selects the responsible Action Officer.
- Attendance: `/city/attendance/dashboard` for the selected dates, and multipart `/city/attendance/upload` using the existing backend CSV/XLSX format.
- IEC: City Admin issue list/details, ULB pending/history/reopening queues and review decisions, Commissioner summary.
- Ward rankings: `/ward-ranking`, calculated by the backend for the selected dates.
- Inspection targets: `/city/targets/performance`, `/city/targets/options`, and `/city/targets` for City Admin target configuration.
- Processing plants: `/modules/processing-plant/entries` and the existing workbook upload. Measurements retain their original units.
- Audit logs, sessions and trash: `/audit-logs/*`, subject to the backend's permissions.

Changes await the backend response before closing forms. Refresh errors and unavailable datasets are displayed explicitly; failed requests never fall back to sample data. Coordinates are plotted from reports, with links to street maps; invented municipal boundaries have been removed.

## Data loading

Authentication loads only the session, city and enabled modules. The workspace then opens immediately; its active section loads the datasets it needs. Audit logs, registration requests, sessions and trash are fetched when those pages are opened. Navigation remains available while a section loads.

Reports and attendance default to the current day in India. Use the From/To controls and Apply dates to request another period. Paginated datasets fetch one page at a time, show loaded/total counts and provide Load more. Page metrics, local filters and CSV exports use the records currently loaded; an explicit notice appears when additional pages are available. Changing city, dates or session cancels obsolete requests. Failed datasets show individual retry controls, and requests have a 25-second timeout.

The existing personnel and beats endpoints return their complete directories without pagination; these responses are cached for the current workspace context. A manual refresh or successful mutation resets the relevant workspace context so active data is fetched again.

## Existing backend limits

The updated backend accepts explicit city context for authenticated Super Admin requests while retaining the signed administrator identity. Other city roles remain restricted to their assigned city. Deploy the matching backend changes before enabling these platform workflows.

The updated backend recognizes the canonical `HMS_SUPER_ADMIN` audit role. City Admin activity logs are restricted to their own city and omit platform administrator activity. Log details redact sensitive fields.

Swachh Assessment uses a separate service and token and remains accessible through the existing portal. KML/KMZ beat bulk imports and Action Officer corrective evidence submission also remain in the existing portal/app. The old demo CSV import and correction-request decision are unavailable because their contracts do not exist in this backend. For beat creation, an existing Area is required under the selected Ward.

City onboarding consists of separate backend writes for the city, administrator and modules. If a later step fails, the error identifies the partially created city; complete its setup in City Administrators and Product & Module Access instead of resubmitting it.

## Role dashboards and RYG

Super Admin manages authorized cities, provisioning, administrators and governance. City Admin manages geography, personnel, assignments and inspection targets. ULB Officer works with inspection queues and IEC decisions. Commissioner has an executive overview, ward drilldowns and operational oversight. Menu visibility follows the authenticated role and enabled city products/modules; the backend remains the authority for every request.

Operational screens share dependent Zone/Ward, module, staff, status, RYG and text filters where applicable. Date presets and custom dates change server queries. Ward rankings retain the backend's performance bands; dashboards do not invent score thresholds. Red means action required/rejected/escalated/overdue; yellow means review or verification pending, including action taken; green means approved/closed/present. Unknown or unassessed values remain grey. Missing scores, shifts and demographic data are displayed explicitly.

## Checks

City Overview separates registered locations, period inspection submissions, unique inspected location IDs, repeat inspections and registered locations still to cover. A location visited three times contributes one unique location and two repeat inspections, including visits on different days in the chosen period. The independent coverage reader follows every report page for each enabled module with bounded concurrency and cancels on date changes. It validates the returned pagination totals; a missing module, missing location ID or incomplete history leaves affected figures unavailable rather than claiming zero or exact coverage. Registered-location coverage uses the inventory returned by the operations-map endpoint for the selected end date; it is not a reconstructed historical register. Inspected locations outside that register are disclosed and excluded from registered-location reach. Coverage measures reach, not cleaning quality or compliance with daily/periodic frequency requirements.

The Commissioner overview uses module cards with separate “Total inspections required” and “Target” values. Total inspections required is explicitly a full-location-coverage baseline: one inspection per registered location, independent of configured targets. It does not invent a daily frequency requirement. Targets such as 5% or 10% retain the backend’s assigned period count and rounding. A change from a target of 9 to 18 leaves a register of 87 locations at 87; with 9 credited completions, achievement changes from 100% to 50% and pending inspections from 0 to 9. Raw/repeat inspections do not replace the official completed count. Coverage continues to use unique registered locations inspected, not target achievement. Configured percentages appear only when supplied consistently by the backend, and no period target is multiplied by the number of days.

Cards keep Unique inspections, Repeat inspections, Coverage and outcome/action counts visible. Inspections done and backend completion details are available in a collapsed details section to avoid repeating counts. Pending inspections means work remaining against a confirmed target; Pending review means reports awaiting SI review. Action taken remains a separate workflow stage, not a claim of verified resolution. Shared wording in `src/services/commissionerTerms.ts` is used in the cards, overview, zone details, charts, exports and assistant. Existing module and staff-role names remain unchanged.

Target falls back to Total inspections required when no configured target is available. This baseline uses one inspection per registered location; unique registered locations inspected count toward its achievement so repeat visits cannot inflate coverage. The zone export omits the source field. Commissioner therefore also uses `/city/users/daroga-performance` rows, which expose `source: ADMIN | DEFAULT`, ward, module, assigned target, credited completions and percentage for the requested IST date range. ADMIN rows identify configured requirements; DEFAULT-only modules retain the full-coverage fallback. Aggregates retain backend prorating and daily credit rules and include default requirements for unconfigured assignments when combined with configured ones. SI review targets are separate and are not added to Daroga inspection requirements. The same source resolution feeds module cards, city/zone summaries, ward details and Nagar Insight. Missing inventory remains unavailable rather than zero. Browser validation uses isolated API fixtures, not live saved-target records.

City Admin Inspection targets now uses `/city/targets/assignments` to select an existing Daroga ? ward ? module assignment.
